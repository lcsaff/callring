# UI 统一管理与彻底重构设计

日期：2026-10-15。

目标是将 UI 从数据操作、业务规则和系统生命周期中解耦，使后续页面、交互和外观调整有明确归属。普通页面迁为 Kotlin、Jetpack Compose 和 MVVM；最终完整删除被替代的旧 UI 方案，不保留旧入口、兼容包装、双路渲染或运行时回退。

范围、Kotlin 与 Compose 技术方向、主题能力、评分配色，以及悬浮窗样式和信息已经确认。小组件字段也已确认，本文按最终决定维护目录、依赖和迁移方案。

UI 与业务侧的接口、字段及行为以 [UI 业务 API 契约 v1](UI业务API契约_v1.md) 和 [Kotlin 契约声明](../contracts/CallringUiApi.kt) 为开发依据。本设计和交互原型中超出契约的示例不能作为新增业务能力的依据；接口调整需先同步契约，UI 不自行增加替代接口或重复业务模型。

## 本轮协作职责

本轮仅开发 UI 侧。UI 侧负责 Compose 页面、ViewModel、UiState、设计系统、主题生成、展示格式化、系统交互协调、悬浮窗展示端口实现、小组件 UI 以及使用正式契约的测试 Fake。生产契约声明和业务 API 实现由另一侧提供。

UI 与业务侧交接 API 注入点、主题预设稳定 ID、`IncomingCallUiSink` 实例，以及新入口和旧引用的切换清单。UI 侧不复制一份生产契约、不实现旧 Java 仓库的临时直连、不将 Fake 注入正式运行入口。共享构建和应用组装变更按双方实际代码协调，保持生产声明只有一份。

整体交付仍要求旧 UI 完全清零。旧 UI 源码及资源由 UI 侧删除，旧业务代码中对旧 UI 的调用由业务侧切换到正式契约端口；移除旧静态事件耦合也须同步完成。UI 独立测试通过不等于生产接入和整体迁移完成。

## UI 目录和职责

新 UI 集中在独立 Android library 模块 `ui/`，源码位于 `ui/src/main/kotlin/com/greatwall/callring/ui/`。按功能组织页面及其状态逻辑，共享视觉规范由设计系统统一提供；`app` 负责应用与业务图组装。

```text
ui/
  app/                       应用入口、导航和外部跳转参数
  designsystem/
    Theme.kt                 主题定义、注册、色板、字体、间距和形状
    ScorePalette.kt          与主题主色独立的评分语义色
    components/              按钮、输入、卡片、设置项和通用状态组件
  feature/
    home/                    首页 Screen、ViewModel 和 UiState
    callers/                 档案列表与编辑的 Screen、ViewModel 和 UiState
    report/                  报表 Screen、ViewModel 和 UiState
    settings/                设置总览与各设置页面
  overlay/                   悬浮窗展示、窗口协调和会话状态
  widget/                    小组件系统入口、配置页面、状态和 Glance 渲染
  state/                     加载、保存、草稿与失效通知等展示状态基础
  format/                    无存储依赖的展示格式化与评分样式映射
```

Android 平台要求的 Manifest、图标、字符串和组件元数据仍在 `res/` 或标准位置管理。普通 Compose 页面不再保留一套旧 View 页面作为备用。Glance 使用的框架资源属于新小组件方案的一部分。

设计系统只定义视觉与基础交互，不承担业务查询、保存、后台任务或页面导航。档案、报表等业务组件放在对应功能目录；同一个业务组件被多个入口使用时，再提取到明确的共享位置，避免形成新的大型 `Ui` 工具类。

## 依赖边界

```text
Screen / 可组合组件
        ↓ 用户操作        ↑ UiState
页面 ViewModel
        ↓
注入的 CallringUiApi
        ↓
业务侧应用层查询与操作
        ↓
Repository 接口与业务策略
        ↓
现有 SQLite、私有设置和文件存储
```

- Screen 接收不可变展示状态和操作回调，不查询数据库、不读写 SharedPreferences、不直接操作文件，也不自行计算评分、免打扰或工作时间。
- ViewModel 属于 UI 层，负责草稿、筛选、分页、加载、保存和错误状态。它通过注入的 `CallringUiApi` 获取数据，不持有 Activity、View、Service 或 WindowManager。
- 应用层组合查询、执行保存和导入导出等操作，复用现有算法与存储。跨页面、悬浮窗和小组件的公共操作放在这里；不为每个简单调用机械增加多层转发。
- 数据层负责持久化和数据一致性，不引用 `ui` 包，不主动调用某个 Activity、悬浮窗实现或 WidgetProvider。
- 组装入口负责连接实现与接口。Android 权限、文件选择、窗口和后台启动等系统操作通过明确的系统接口协调，不进入可复用的页面组件。
- 数据模型和展示模型明确分工，UI 不持有可修改的数据库实体作为共享状态。展示格式化不能通过 WidgetProvider 间接访问。

原 `ManagementEvents` 中直接刷新小组件和悬浮窗的耦合要被替换。新方案在数据变更成功后发布变更通知，各入口按自身生命周期加载新状态。后台来电、进程恢复和小组件更新继续有系统入口，不依赖某个页面或 ViewModel 正在运行。

## API 契约接入规则

生产接口和类型归属 `com.greatwall.callring.application.api`，由业务侧统一维护一份声明。UI 仅注入并消费这份契约，不复制另一套同名类型，不直接调用现有 `CallerRepository`、`AppSettings`、`ManagementEvents` 或业务策略类。文档目录中的声明不直接当作生产源码使用。

`CallringUiApi` 已提供首页、档案、报表、设置、铃声、运行条件、小组件绑定和变更通知能力。各页面按契约调用对应聚合接口，不在 UI 中拼接仓库查询、重算评分或反推工作时间。所有 `suspend` 方法按主线程安全使用，阻塞 I/O 的线程切换归业务实现；不沿用旧 `Ui.run()` 执行器。

- `ApiResult.Failure` 按错误码、字段路径和所需能力处理；提示文字不作为条件分支。`CancellationException` 正常传播，不显示为保存失败。
- 编辑草稿与返回快照分开管理。用户没有修改白名单时，`SaveCallerProfile.whitelisted` 传 `null`；单独更改白名单使用目标值 `setWhitelisted(number, enabled)`，不使用翻转操作。
- 职位关系使用 `PositionRelation` 和 `PositionOption.relationToMe`，不在 UI 中比较层级；未知通话时长 `null` 与真实零秒 `0` 分别展示。
- 报表直接展示整个日期区间的 `totals`、`score` 和 `quality`；筛选只影响 `details`，分页不影响汇总。导出使用 `ReportExportQuery`，不受明细筛选或分页限制。
- 分页从 0 开始，页大小为 1–200。相关数据变化后从第 0 页重查；超出末页时依据真实总数修正页码，不依赖后端自动回跳。
- 保存成功表示业务提交已完成。取消等待不代表撤销写入，不自动重试新增职位、请假等非幂等操作。
- 音频、日历和 CSV 通过系统选择器获得授权的 `content://` URI，再包装为 `DocumentRef` 交给 API；UI 不打开文件内容、不接受本地路径作为替代入口。

主题预设的稳定 ID 由 UI 侧定义，并在业务默认配置接入前交接；显示名称与 ID 分开维护。业务侧将 ID 当作不透明字符串存储。遇到未识别的 ID 时只用联通红进行显示兜底，不静默覆盖保存值，也不为旧 UI 增加别名或迁移分支。

### 变更与时间刷新

UI 使用 `changes.observe()`。首次收集发出的全部领域失效通知触发初始加载，后续根据领域、号码和组件 ID 决定重查范围；`numbers=null` 或 `widgetIds=null` 表示不限对象。通知只表达失效，不能直接当作完整 UiState。

`dataRevision` 只在当前进程内关联业务变化，不代替页面请求序号，也不跨进程比较。运行条件通知可以沿用当前修订号，不能仅按修订号去重所有事件。页面恢复前台、权限返回、组件系统更新和新悬浮窗会话都重新查询。

UI 按 `nextBoundaryEpochMillis`、日期和时区系统事件重查时间相关展示；提示为空时，活动界面使用有生命周期的适度刷新。后台来电判断仍由业务侧按实际时刻执行。

### 来电展示端口

UI 实现契约中的 `IncomingCallUiSink`，由组装入口注入来电处理流程。`show()` 接受任意线程调用并迅速返回，内部安排线程和合法的窗口服务启动，隔离窗口及启动异常，不等待数据加载，不影响 Telecom 已提交的响应。

使用 `IncomingCallUiRequest.sessionId` 隔离每次会话，不能用号码替代会话标识。通过 `getOverview(OverviewQuery(number, startedAtEpochMillis))` 加载概览；本次即时决策使用请求自带的 `decision`，不按之后的设置重算。

### 契约范围内的原型调整

首页按 `HomeData` 展示铃声、运行条件、当前工作状态、最近来电、统计开关、悬浮窗开关和免打扰模式。当前 v1 没有今日来电及今日非工作来电汇总，原型中的两个数字卡片不进入本轮实现，不能以固定数字填充或由 UI 自行统计。

档案搜索只实现 `CallerSearch.text` 与分页支持的能力。原型中的白名单、有来电记录快捷筛选不作为 v1 功能；不能只筛当前页冒充全量筛选。需要这些能力时先扩展契约。

## 页面状态和交互

主要应用页面由新的应用入口与 Compose 导航承载。小组件配置等系统要求的独立入口直接使用新实现。导航参数采用集中定义的号码和页面参数，通知、悬浮窗、小组件及调试工具统一跳转到新入口。

| 功能 | UI 职责与重构要求 |
| --- | --- |
| 首页 | 展示当前运行条件、工作状态、最近来电和快捷操作；音频导入、验证和保存从界面中抽出 |
| 号码档案 | 搜索、分页、档案详情与新增编辑使用独立状态，复用档案展示组件 |
| 档案编辑 | 草稿与已保存数据分离，保存失败保留输入，刷新职位选项不能覆盖未保存内容 |
| 号码报表 | 汇总、筛选和逐次明细分组展示；日期、分页和筛选状态集中管理；导出使用应用层提供的数据 |
| 管理设置 | 总览按工作安排、请假与日历、免打扰、评分、职位、铃声与显示、权限等功能进入子页面 |
| 外观设置 | 编辑自定义主色，选择预设及深浅模式，预览并保存配置 |
| 小组件配置 | 仅按最终确认的字段和交互实现，不将旧配置页结构继续保留为兼容入口 |

页面通过 StateFlow 暴露 UiState，并按生命周期收集状态。需要跨配置变化和进程重建恢复的轻量草稿、筛选与导航参数使用合适的保存状态机制；业务数据继续持久化，不把 ViewModel 当作数据库。

异步读取使用请求标识和当前号码等参数判断结果是否仍有效。旧请求不能覆盖新号码或新筛选结果。保存过程防止重复提交，数据库操作保持原有事务语义；写入成功后的通知不能因为页面已离开而丢失。普通数据刷新只更新必要状态，不重建并清空编辑表单。

## 主题和设计系统

主题使用稳定标识、显示名称、浅色方案和深色方案定义。页面和组件消费颜色角色，不根据具体主题名称编写分支。添加预设时只增加主题定义和注册记录。

自定义主题保存用户选择的主色，通过 Material 配色工具生成配套的主色、容器色、背景、表面、文字和边框颜色。用户可以用颜色选择器或六位十六进制色值调节，实时预览后应用保存。配色生成支持从单一主色构建完整方案，依据 [Material Color Utilities](https://github.com/material-foundation/material-color-utilities)。

外观偏好通过 `settings.getAppearance()` 和 `settings.saveAppearance()` 读取和保存，UI 不另建一份持久化配置。`AppearanceSettings` 使用 `ThemeSelection`、`presetId`、`customSeedRgb` 和 `ColorMode`；自定义 RGB 为不带透明通道的 `0x000000..0xFFFFFF`，`CUSTOM` 必须有色值。切换预设保留已保存的自定义主色；默认联通红、跟随系统。输入中的预览色与已提交偏好分开管理，无效色值不能覆盖当前有效配置。用户选定的主题不会被系统壁纸配色覆盖；跟随系统只决定深浅模式。

所有入口共享颜色语义、字体层级、间距、圆角和图标规范。普通页面和悬浮窗复用适用的 Compose 组件；小组件通过自己的组件映射使用同一套设计值。Material 3 的颜色、字体和形状体系支持这种集中管理，参见 [官方主题文档](https://developer.android.com/develop/ui/compose/designsystems/material3)。

评分有独立的样式映射：

| 分数 | 色相 | 表达 |
| --- | --- | --- |
| 80–100 | 绿色 | 不受欢迎程度低 |
| 60–79 | 黄色 | 不受欢迎程度中 |
| 0–59 | 红色 | 不受欢迎程度高 |
| 无记录 | 中性色 | 暂无评分，不判断程度 |

浅色与深色模式可以调整这些语义色的明度以保证可读性，但不能改变其色相含义与分档。主题变化不改变评分颜色。评分显示保留数字、分值说明和可访问文字，不只依靠颜色传达结果；在彩色卡片上使用可读的中性承载区域。

## 悬浮窗和小组件

悬浮窗分为服务生命周期、窗口操作、会话状态和 Compose 展示。窗口操作负责拖动、安全边界、键盘与焦点、挂载和移除；会话状态负责当前号码、加载、收起、编辑、保存及待关闭状态。服务负责系统回调和运行条件，界面不直接读写 Repository。

已确认的信息包括号码档案、相对职位、评分及依据、次数、工作分类、来电决策和白名单状态。保留现有隐私行为：锁屏隐藏个人信息，仍在响铃时解锁可恢复显示，已结束摘要不会重新自动弹出；编辑草稿可以保存或取消。过期请求不能附着到新来电会话。

小组件采用 Glance，分离系统接收、绑定存储、数据加载和渲染。绑定与操作必须按 widgetId 隔离，更新不能依赖 Activity 或页面 ViewModel。Glance 有独立的组件体系，不能把普通 Compose UI 组件直接混入小组件，参见 [Glance 官方说明](https://developer.android.com/develop/ui/compose/glance)。

小组件采用已确认字段：小尺寸显示姓名/号码与当前评分，大尺寸增加部门/职位；提供查看报表和明确目标值的白名单切换，大尺寸另提供更换号码与刷新。次数、最近来电等原型示例未纳入本轮字段。

- 清除旧 UI 的执行器、静态 Activity 集合、重复格式化方法、重复渲染和废弃导入。

禁止保留旧 Activity 别名、旧包名转发类、新界面失败后退回旧界面的分支、运行时新旧开关，以及同一功能的 View 与 Compose 两套 UI。实现过程中可以按职责逐步替换，交付验收时这些残留必须为零。

系统组件身份直接切换到新路径，旧组件路径不作兼容。已有桌面小组件需要重新添加；应用内数据库、业务设置、档案、历史记录和选定音频保留，不通过清数据完成迁移。Java 业务策略和存储实现承担的是继续有效的业务职责，不因 UI 更换而删除或重复改写。

## 实施顺序

1. 审阅整体设计，明确新入口、依赖边界和删除清单；小组件字段在其实现前另行确认。
2. 核验并锁定相互匹配的稳定 Kotlin、Compose、AndroidX、AGP 和 Gradle 版本。最低 Android 版本保持现有 29；targetSdk 的变化必须说明对后台、窗口和权限行为的影响。
3. 建立设计系统、主题持久化、评分样式和应用层边界，先验证主题生成、评分分界和数据操作。
4. 实现主要 Compose 页面、ViewModel、导航和外部跳转，完整迁移现有功能。
5. 重构悬浮窗；在小组件字段确认后实现 Glance 小组件及配置入口。
6. 移除旧方案，迁移测试、脚本和文档，执行整体构建、结构检查和实机回归。

每个阶段都服务于同一个完整交付，不单独发布长期并存的新旧 UI，也不以界面已能打开作为重构完成条件。

## 验收标准

### 结构

- 人工编写的 UI、主题与展示状态集中于 `ui/`，标准 Android 资源留在规范目录。
- 页面组件不依赖数据库、SharedPreferences、业务策略计算或具体 Repository 实现。
- ViewModel 不持有 Activity、View、Service、窗口或界面组件引用。
- 数据和业务层不反向依赖 UI；展示、数据加载、保存和系统生命周期的职责可独立理解和测试。
- UI 对业务的唯一入口是正式 API 契约；不存在重复生产声明、旧静态类调用或自行推导业务事实的路径。
- 旧方案清单中的类、无效资源、旧组件路径和兼容分支全部移除，源码、资源和可执行工具中无失效引用。

### 功能和视觉

- 现有档案、报表、设置、导入导出、权限和音频功能全部迁移，数据含义与业务规则保持一致。
- 三套预设、自定义主色、深浅模式及保存恢复在页面、悬浮窗和小组件中一致生效。
- 评分在 0、59、60、79、80、100 和无记录时显示正确颜色，切换主题不改变分档。
- 表单草稿、保存失败、重复操作、旧请求返回、页面重建和跨入口刷新有明确结果。
- 已确认的悬浮窗样式、显示信息、拖动、键盘、收起及锁屏隐私行为通过回归。
- 小组件按最终单独确认的字段与交互验收，验证多组件绑定、点击和刷新相互隔离。

### 验证方式

为状态转换、异步请求有效性、主题配置与评分语义提供有意义的单元测试。设备测试迁移到新的入口与语义定位，不为继续使用旧测试而保留旧 UI 类、旧 View 层级或旧服务私有字段。

UI 测试可使用内存 Fake，覆盖无记录、未知时长、真实零秒、权限缺失、保存失败、停用职位、关联待核对、历史更正、旧查询晚返回及取消。Fake 使用正式契约，限定在测试或设计预览中，不作为生产运行后端，也不依赖旧 UI。最终联调和验收连接业务侧的生产 API 实现。

构建与检查沿用项目任务：

```powershell
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug :app:assembleRelease :app:lintDebug :app:assembleDebugAndroidTest --console=plain
```

实机回归使用隔离测试数据，覆盖页面、悬浮窗、小组件及原有来电链路。未完成的实机项目明确保留为未验证，不沿用旧架构的历史通过记录作新方案验收。
