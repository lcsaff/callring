# 业务解耦重构实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 实现 UI API v1，将档案、日历、来电、报表与系统适配分开，使新 UI、后台任务和来电入口共享业务能力。

**Architecture:** 在现有单个 `app` 模块内按业务组织应用服务，稳定接口位于 `application/api`，SQL 和 Android 调用位于数据及平台适配层。现有算法继续复用；生产来电使用独立的决策快照及事件写入路径，UI 聚合与历史计算不进入实时响应链。

**Tech Stack:** Kotlin、Java、coroutines、Flow、Android SQLite、原生 Telecom/JobScheduler。Kotlin、协程及 Android 工具链版本由 UI 重构一方统一维护，本计划消费同一套版本；不自行升级 AGP、Gradle、compileSdk 或 targetSdk。

## 并发和持久化约束

### UI 查询与保存

- 所有生产写入经过 `MutationCoordinator`，包括来电登记和补全。迁移中的旧入口也使用该协调器；禁止只有新 API 发通知而旧入口绕过。
- SQLite 聚合查询在协调器保护的捕获阶段复制所需记录与配置，确保单次结果基于同一数据状态；排序、评分、CSV 拼装在捕获后完成。独立偏好各读取一次，运行条件另外采样。
- 同一协调器串行执行写命令；校验、提交失败回滚。提交成功后完成决策快照发布、递增修订号及失效通知，之后才返回成功。
- 会影响决策的修改，在提交前构建对应候选快照；提交后只进行不会访问磁盘的原子引用替换。不得在已经提交后因重新查询快照失败而向 UI 报告“未保存”，也不得在提交前发布新配置。
- 调用者等待写入锁时仍可取消；开始提交后，提交结果和通知由应用生命周期任务保证完成。不得让取消造成“已提交但永不通知”。
- SQLite 读取捕获和历史事务可以让 UI 等待后台结果；实时来电不等待这个协调器。

### 来电快速路径

`DecisionSnapshotStore` 持有不可变配置历史、当前日历/请假、白名单及免打扰配置，通过原子引用发布完整版本。每次来电按其实际时间求值，不缓存“现在是否工作”的布尔结果。

首次进程启动可在专用决策线程装载快照；未完成装载仍受原 800ms 超时保护，超时保留系统铃声。装载成功后，正在进行的报表或历史事务不能阻止读取上一已提交快照。配置修改必须在事务提交后、API 成功返回前发布新快照；失败保留旧快照。快照所用集合深拷贝，不共享可变的 `WorkSchedulePolicy.Config`。

事件登记使用独立写入队列。先形成决策结果，再尽快提交事件任务；系统响应不等待 SQLite 获得写锁。来电开始时间、账户、首次分类快照和最终决策按会话关联，最终决策即使先于记录写入完成，也必须在写入后正确更新。后台任务或进程退出前未能落盘的事件仍有平台恢复边界：具备系统通话记录权限时可按原有方式补全；没有权限时不能承诺零丢失。不能把内存排队描述为持久化成功。

历史更正与事件排队并发时，首次分类来自实际决策快照；当前分类按写入时适用的更正计算。不能用稍后配置覆盖首次分类或已发生的铃声决策。保持 `screening_key` 和系统 log ID 的幂等规则，不引入第二套计数来源。

- [ ] `ApiRunner` 使用注入的 dispatcher 和内部 `DomainFailure`，基础实现如下；SQLite 和权限的精确错误在各适配器转换，不按异常文本判断：

```kotlin
class DomainFailure(val error: ApiError) : RuntimeException(error.message)

class ApiRunner(private val io: CoroutineDispatcher) {
    suspend fun <T> run(block: suspend () -> T): ApiResult<T> = withContext(io) {
        try {
            ApiResult.Success(block())
        } catch (cancelled: CancellationException) {
            throw cancelled
        } catch (failure: DomainFailure) {
            ApiResult.Failure(failure.error)
        } catch (failure: IOException) {
            ApiResult.Failure(ApiError(ErrorCode.IO_FAILURE, "文件操作失败", retryable = true))
        } catch (failure: Exception) {
            ApiResult.Failure(ApiError(ErrorCode.INTERNAL, "操作暂未完成，请重试"))
        }
    }
}
```

- [ ] 第一版采用全领域失效，满足 v1 合并通知的约定，不先建立复杂的对象级事件总线。完整的关键实现为：

```kotlin
class DefaultChangeFeed : ChangeFeed {
    private val revision = AtomicLong(0)
    private val signals = MutableStateFlow(0L)

    override fun observe(): Flow<DataChange> = signals.map {
        DataChange(revision.get(), DataDomain.values().toSet(), null, null)
    }

    fun revision(): Long = revision.get()

    fun dataCommitted(): Long {
        val next = revision.incrementAndGet()
        signals.update { it + 1 }
        return next
    }

    fun runtimeChanged() {
        signals.update { it + 1 }
    }
}
```

这里使用 Kotlin、Java 原子类和 coroutines 标准 import。每次订阅自然得到一次失效；StateFlow 合并后剩下的仍是全部领域失效，不会遗失领域集合。运行状态通知不必递增业务修订号，UI 不可只按 `dataRevision` 去重。

- [ ] 为提交顺序建立单一协调器：写入锁可取消等待，提交、缓存发布和通知在有界的非取消完成区间中进行；数据库事务失败不增加修订号。文件读取和评分不得整体包进 `NonCancellable`。
