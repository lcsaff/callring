# T10 装配收口补充准备（非验收）

2026-10-21，基于b1bf4b0只读复核；未运行Gradle或修改业务。与t10-preparation.md合用，实施前复核T09b源版本发布变更。

## 剩余 Context 消费者

RuntimeService、RingtoneService、WidgetBindingsService仍用with(context)，CallringBackend还将已迁窄服务的构建、DecisionInputs补丁与command绑定放在Context。T10应在明确装配处构建这些服务；总装配可以知道全部依赖，服务只能知道自己声明的能力。DecisionInputs缓存及窄补丁保持共享生命周期，bound不能新建独立缓存或协调器。Context的io/write/validation/runtime辅助可复用既有UseCaseRunner及明确函数，不能以Context2/Dependencies包回同一组对象。

SettingsApi/UiEditsApi当前只是组装已迁服务；移入CoreAssembly后删除旧Context工厂及其测试引用。checkNumber使用唯一NumberIdentity。T09b仍可能调整captureCore/完整快照入口，T10以其最终端口为准。

## 必须实际消除的发布路径

- WidgetBindingsService先让AndroidPreferences.save/remove内部commit，再重复publishScopes，并以capture未变时changed(preferences)兜底。相同绑定保存/不存在绑定删除仍会发布；不得将此行为原封搬到窄服务。改为最终值差异的唯一提交者，真实变化一次、noop零发布，失败零发布，命令仍记录。PreferenceStore存储实现退出业务决定与第二次发布，保留持久化失败恢复。
- RingtoneService以全局capture前后比较推断平台是否发布，并notifyChanged(core)兜底；并发无关提交会改变判断，noop也可被兜底变更。应显式返回/提交实际delta并移除比较与fallback。音频复制/验证在fence外，最终generation保护、持久化与发布同边界；预览/停止和自然播放结束必须有同一真实runtime范围。
- RuntimeService请求日志同步的guard、权限判定与调度次序保持。运行状态读取由窄RuntimeProbe加completeRuntimeStatus，不能经完整settings/State。读取installedWidgets应由UI桥注入，不让Graph依赖具体widget实现。

## 组合与依赖

CoreNumberDeletionApi与app NumberDeletionService目前各有一套顺序/数量/匹配逻辑；最终应使用同一backend组合服务及必需的录音/绑定能力，避免保留“核心版本”业务fallback。测试使用明确空能力假端口，不能据测试需求保留生产Unavailable分支。CallringBackend的Unavailable能力与Graph覆盖装配应在本片改为明确生产能力组合，评估后同步现有测试，不新增假成功默认实现。

BackendGraph还承担adoptIdentity、组合command继续、自有提交、来电登记后的录音session/phoneState编排、JobScheduler具体查询及具体widget安装查询。依照Core/Recording/Conversation/UiBridgeAssembly拆分；惰性打开、close不初始化未用依赖、incoming先drain后关闭存储、不会持lifetime锁等待executor等现有行为必须保留。

RecordingPorts/AiClient仍把java.io.File传入backend，Workflow构造File；该路径使用音频引用/流端口迁移后同步所有client及fake。RecordingStore.isDeleted默认false应核对真实必需能力，迁移时删除能绕过tombstone的默认实现。nextRunAt/processPending当前all()全归档扫描应改最早时间/到期候选能力；listArchives作为显式列表功能仍可读取所需集合，不将普通单号码影响预览与完整文本绑定。

以上均为后续实现门，不是已完成证据。规格审查应同时核对真实publisher/sourceVersion、命令冲突与唯一累计失效，不能只检验包名移动。

## 多资源提交及既有默认入口（390c651只读补充）

当前CommandCommitter仅publishCore，RecordingStore.updateSettings却按publishScopes→changed(recordingConfig)→changed(aiConfig)多次推进。AI+录音组合patch应一次持久化、一个全局marker/累计impact，同时仅推进实际变化的资源版本各一次；不要为复用core提交者而将配置错记到core，也不能把一次组合拆成多个业务提交。可以收紧现有发布原语支持明确资源集合，服务从事务前后真实字段生成delta；无需新增万能资源注册框架。noop仍记录命令，失败不发布。

AndroidRecordingRuntime还有saveSettings、selectSystemFolder与bound.saveSettings直接写配置；迁移AiSettingsService时同步切到唯一backend配置命令，不能在data保留另一套validate/fielddiff/publish业务。新导入音频即使RingtoneSettings展示值相同，也可能替换了音频内容，不能仅用展示DTO相等认定noop；重复关闭/恢复内置则按实际选择与播放变化判定。保留generation及最终文件/元数据原子性，复制验证在fence外。

AudioController现有无command/带command默认重载及guarded_commands_unavailable是迁移收口对象，改窄能力时同步所有真实调用与fake后删除旧入口，不能只迁RingtoneService工厂。PreferenceStore.listBindings默认不可用与RuntimeProbe.getInstalledWidgets默认UNKNOWN同样须核对实际消费者，最终生产能力显式注入；不要用测试需求保留生产默认fallback。

当前生产搜索未发现RecordingConfigurationPort的getSettings/saveSettings/testConnection实际调用方，仅AndroidRecordingRuntime/其bound实现和RecordingCapability组合声明；测试可能仍用旧管理入口。迁配置时逐一核实并删除无生产消费者的旧管理方法/组合接口，测试改明确seed/新窄命令；不要机械地把这些旧完整配置写入口搬到backend作为第二套设置业务。

旧AiSettingsService的patch在store.updateSettings退出guard后才用aiView()/recordingView()读取当前domain revision；patchRecording还先调用afterSave。若此间另一线程提交配置，返回的旧saved值可能贴较新revision，密钥configured布尔也不能揭示此差异。迁移时在同一最终提交fence内捕获返回值及相应已提交version，再在外部做folder/live投影与afterSave；用真实latch验证“旧值不能贴新版本”，不将provider IO放回fence。

## T10c当前收口边界（119e208只读补查）

以上历史配置/小服务问题已由T10a/b完成，以各片review为准。当前BackendContext实际只剩服务组装、command bound、DecisionSnapshot共享缓存及其窄补丁、checkNumber和旧observe；SettingsService/UiEditsService仍以with(context)组装API。将其改明确装配和仅接所需服务的API组合，删除BackendContext类/引用/旧工厂；服务不得接受改名的CoreAssembly作为万能上下文。Decision缓存和quiet/whitelist/calendar/leaves/work/statistics/overlay补丁须共享同一生命周期，bound不创建第二缓存，保留冷读取与预热语义。

app现有RecordingAssembly已是实际组合根；继续拆CoreAssembly、ConversationAssembly、UiBridgeAssembly，Graph保留总生命周期。具体widget安装和通知桥归UiBridge；具体Job查询与AI源、完整快照、foreground资源接线归ConversationAssembly；incoming登记后的session/phoneState及sync恢复明确注入控制器。关闭先drain incoming且不持lifetime锁等待executor，保留diagnostics在drain期间可用、未初始化资源不打开。

生产CapabilityFallbacks.kt需整体退场，CallringBackend不要通过实现完整CallringUiApi再塞五个Unavailable对象制造半可用后端。可以以明确core能力组合完整UI API，或要求真实能力显式装配；不得留下“core-only测试版本”生产构造器。b3会先调整组合删除/身份能力，c实施前按其最终签名复核。

contracts里还存在aiUnavailable默认方法：CallringUiApi.commandApi直接return this、adoptIdentity，UiEditsApi七方法、CallersApi三方法、WidgetBindingsApi.listBindings、RecordingApi.inspectSystemRecording、AiSettingsApi.patchCombined/testDraft、ConversationApi.sendTo/continueTask。c收口时逐个核查并移除只为旧实现/测试省略能力存在的默认体，改必需override；真实生产实现显式具备能力，测试共享fake留在测试源中。aiUnavailable helper最后调用方迁出后删除，不保留新的生产Noop/Unsupported同义替代。参数的真实产品默认值（例如LocalSecretChange.Keep）与缺能力默认体不同，不能机械删除。

这类清理保持对外方法签名和真实产品行为，内部实现不能再悄悄漏实现能力。docs/contracts/current-api.md是经过审查的当前源码库存，可随有依据的必需方法收紧更新；原T02历史12API快照与ai-operation-compatibility.json/pin继续冻结，不用改历史样本放过守卫。T11另按计划删除DataChange及nullable/default snapshots，不把它混作c已完成。
