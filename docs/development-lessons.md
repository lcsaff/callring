# Callring 开发经验

本文汇总 Callring 的开发实践、交付经验和开源方案评估方法。项目现行规则见 [PROJECT.md](../PROJECT.md)。

## 从改动中留下的经验

| 场景 | 可复用经验 |
| --- | --- |
| 分层与迁移 | 页面、AI、系统入口共用正式业务命令。迁移完成后删除旧入口，兼容读取留在唯一编码器。号码规则从单条改为多条时，分别验证旧配置、缺字段、显式空列表和非法值，并覆盖所有实际消费者。 |
| 存储与刷新 | 原始事实与后续修正分别保存。聚合读取使用同一事务，提交后按实际变更发布失效，同时验证无关 loader 的调用次数保持不变。 |
| 草稿与异步结果 | 自动保存保留编辑基线，串行提交最新合法草稿。预览、导入和更新检查在关闭或版本变化后隔离迟到结果。试听停止命令只控制试听，保留真实来电独立的生命周期。 |
| 系统录音导入 | 将目录发现、文件稳定、规则匹配和入库分开验证。冻结批次条件，复制前后复核文件及规则版本。使用稳定来源身份去重，显式删除后的墓碑阻止旧文件再次导入。 |
| 删除与静默补全 | 档案和录音按各自的生命周期管理。删除档案时记录删除边界，避免旧分析重新建档。先持久化付费分析，再执行可独立重试的本地补全。号码无法建档时仍保留录音的转写和分析。 |
| AI 与外部协议 | 发现、授权、执行和回执使用具名目录。写入提交后独立读回，部分提交逐项核对，结果未知先查状态再决定重试。协议兼容性以冻结基线和具体模型证据为准。 |
| 验证与交付 | 区分实际执行、缓存命中、模拟服务和真机结果。固定音频可验证解码与持久化，真实来电、厂商后台调度和在线服务需要对应证据。最终源码、CI、标签与发行产物使用同一提交。 |

仓库的项目专用 Skill [callring-delivery](../.agents/skills/callring-delivery/SKILL.md) 用于开发收尾、提交合并推送、版本递增和 APK 交付。具体命令、验证范围和发布条件见 [PROJECT.md](../PROJECT.md) 的“构建与统一验证”和“版本与交付”。

## 评估项目寻找开源方案

1. **先定义要解决的问题。** 写清当前实现、需要补齐的能力、验收样例和必须保留的行为。对 Callring，按场景列出 Android 版本、系统权限、厂商行为、离线能力、已有数据及模块边界等约束，并检查仓库内是否已有可复用入口。
2. **按能力和平台约束找候选。** 用能力名称、平台 API 和具体限制组合检索，从官方文档、源仓库、发布记录、问题追踪和包仓库交叉核对。记录检索日期、候选链接和评估版本或提交。优先查清关键能力是否已经发布、实际走了哪条系统路径，以及仍有哪些设备限制。
3. **先过硬性条件，再比较接入成本。** 核对许可证及分发义务、传递依赖、最低系统版本、构建兼容性、权限和数据流。再比较维护活动、升级路径、公开安全问题、依赖体积、性能、替换成本和停更后的维护负担。把许可证待确认、设备未测和维护状态不明分别记录。
4. **用最小原型验证最难的路径。** 固定候选版本，在隔离环境用同一份样例对比现有实现。先跑最可能决定取舍的场景，例如真实 SAF 目录读写、旧数据迁移、取消后资源释放或目标设备上的后台行为。记录验证条件、结果和剩余缺口。
5. **留下可复查的取舍。** 记录采用依赖、参考实现、自研或暂缓的理由，以及对应证据。采用时说明接入模块、固定版本、许可证义务、维护责任和退出路径。后续遇到 Android 行为、许可证或上游维护状态变化时，按同一验收标准复评。
